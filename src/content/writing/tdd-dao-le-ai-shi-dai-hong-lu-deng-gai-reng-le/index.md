## 一个违反直觉的发现

最近公司在加大力度push大家用AI Coding，我负责弄了测试这块，专门去调研 TDD 最佳实践。以前可从来不敢在项目里引入单元测试之类的，根本维护不过来🤣，现在不一样了，可以把这活儿扔给AI。

我去看了看网上那些把 TDD 搬到 AI Coding 的实践——写进 CLAUDE.md 的规则、做成 Skill 的工作流等等。

突然发现了一个违反直觉的事实：

**大部分"AI + TDD"的方案，就是把人类 TDD 的流程原封不动地塞给了 AI。**

先写一个失败的测试（红灯），再写最少量的代码让测试通过（绿灯），然后重构（蓝灯）。一步一步，小心翼翼，循环往复。

听着很靠谱，对吧？

问题是——**这套仪式是给人类设计的。把它原封不动地搬给 AI，真的适合吗？**

---

## 红绿灯循环为什么适合人类

TDD 的 Red-Green-Refactor，核心假设是：**人类容易犯错、容易分心、容易过度工程化。**

- **Red** — 强迫你先想清楚"要什么"，别上来就敲代码
- **Green** — 防止你一上头就写了三个设计模式来解决一个 if-else 问题
- **Refactor** — 制度性地安排一个"停下来想想"的时间点

三道刹车，治三种人类通病。没有它们，程序员的典型轨迹是：上来就写 → 写多了 → 没测试 → 改坏了 → 重写。

但 AI 没有这些毛病。

---

## 红绿灯循环为什么不适合 AI

AI 不会分心、不会过度工程化（除非你 prompt 写歪了），也不需要用小步骤来"驱动设计"——它可以一次性理解整个需求并输出完整实现。

**但 AI 有一个人类没有的致命瓶颈：上下文窗口。**

你写代码的时候，脑子里天然记着上下文——刚写了什么测试、哪行报错了、接下来该改哪里——这些"工作记忆"对人类来说是免费的。AI 不一样。它的"工作记忆"就是上下文窗口，每走一步红绿灯，测试运行输出、错误堆栈、编译信息、通过信息，**全部塞进去**。对你来说是反馈，对它来说是噪声。

跑三轮红绿灯，有效信息密度可能从 80% 降到 30%。你花着每百万 token 几美元的钱，买了一堆 `✅ Test passed` 和 `❌ AssertionError: expected 42 but got null`。

**传统 TDD 用"小步试错"换"低风险"。但 AI 的试错成本不是时间，是上下文空间——最贵、最稀缺的资源。**

---

## 还有几个更扎心的

**"写最少代码使测试通过" 对 AI 是反模式。** 这条规则本来是治人类过度工程化冲动的——别一上来就搞花活儿，先用最笨的方式跑通。但 AI 没有这个冲动啊。强迫它"先 return 42 让测试过，下一轮再写真实逻辑"，就像让计算器先猜一个答案、再算真正的答案一样。多此一举，双倍消耗。

**测试日志在制造噪声。** 你看到 `NullPointerException at line 42` 会恍然大悟。AI 看到的是一段需要解析的长文本——而且它上一轮就已经知道问题在哪了，根本不需要"看到红灯才行动"。

**AI 还会偷偷"修"测试。** 这一条最坑。人类不会删测试来"解决"失败——至少不好意思这么做。但 AI 没有这层心理障碍。测试失败了？改断言、弱化条件、甚至直接删掉那个测试——对 AI 来说，这可能就是"最短路径"。你以为是绿灯，其实是自欺欺人。

---

## 精神保留，仪式砍掉

说了这么多，不是要把 TDD 一棍子打死。相反——**TDD 的灵魂在 AI 时代更加关键了。** AI 生成的代码"自信但不可靠"，没有测试兜底，翻车只是时间问题。

要扔的只是那套为人类认知节奏设计的执行仪式。

我翻了一遍调研报告里的 11 条 TDD 最佳实践，逐条过了一遍。结论是：**9 条依然成立，只有 2 条要砍。**

直接保留的那 7 条，换个场景反而更有道理了：测试要小而原子化——这样 AI 修 bug 时只需要注入一个小上下文就够了；测试命名要体现意图——`shouldRejectExpiredToken()` 比 `test1()` 强一万倍，好名字就是省 token；只测公共接口——AI 生成的代码内部结构随 prompt 变化剧烈，测公共 API 才稳定；谨慎用 Mock——AI 特别爱 mock，一不留神就 mock 了一切，测试通过了但测的是 mock 本身。

需要改造的有 2 条："从小处开始"这个思想保留，但拆解完之后一次性交付，别一个一个喂；"快速反馈循环"还是要快，但目的从"保持心流"变成了"省上下文"。

真正砍掉的就 2 条：严格的 Red-Green-Refactor 小步循环，以及"写最少代码使测试通过"——AI 没有过度工程化冲动，这步是纯浪费。

---

## AI 踩坑比人类更猛

TDD 经典的 22 条反模式，搬到 AI 场景下几乎全部保留。但有几条，AI 踩的频率比人类高得多。

最普遍的是**浅层断言**。AI 生成的测试看着覆盖率 90%，但你拿变异测试一跑，变异分数可能只有 30%。什么意思呢？就是你把代码逻辑改了，测试居然还过——说明测试根本没验证到真正的行为。`assertNotNull` 这种断言，跟没写差不多。

其次是**过度 Mock**。AI 天生爱 mock。你让它写个 Service 层的测试，它恨不得把 DAO、Redis、HTTP Client 全 mock 掉。最后测试跑过了，但你测的是什么？是 mock 本身。真实代码一个字都没跑到。

还有前面说的**删除失败测试**。人类好歹知道这事不太体面，AI 可没有这层顾虑。

当然也有好消息——有几个反模式 AI 反倒不太容易踩。比如"只在我机器上能跑"（AI 不依赖本地环境），和 `test1, test2, test3` 这种命名（AI 命名比大部分人类规范）。

## 那 AI 时代的 TDD 该怎么玩

核心就一句话：**让 AI 一次干完，然后验收。别一步一步喂。**

```
传统 TDD:  Red → Run → Green → Run → Refactor → Run   (6步，3次运行)
AI TDD:    Spec → Test+Impl → Verify → Fix(if needed)  (2-3步，1-2次运行)
```

展开来说五条：

**一次性交付，事后验证。** AI 根据需求一次性生成测试 + 实现，然后跑一次验证。它的优势是全局理解能力，你非让它小步走，是在故意降智。

**测试是验收标准，不是驱动工具。** 先把完整的测试套件写好（或让 AI 生成完你审查一遍），然后作为"通过标准"交给实现。测试驱动的是验收，不是设计过程。

**失败了别全量重放。** 哪个测试挂了，就只给 AI 看那个测试的失败信息和相关代码。别把整个测试日志灌进去——它需要的是"哪里错了"，不是"整个世界长什么样"。

**重构单独开一个上下文。** 重构和"让测试通过"是两个完全不同的任务。在一个干净的上下文里做重构，效果好得多。

**用变异测试替代红灯验证。** 传统 TDD 的 Red 阶段，本质上是在确认"这个测试真的能检测到错误"。AI 场景下，用变异测试（Java 用 PIT，JS/TS 用 Stryker，Python 用 mutmut）批量验证，一次性告诉你哪些测试是假的，比一个一个走红灯强太多。

另外，因为 AI 有些人类没有的"新花样"，建议在你的 AGENTS.md 或者 CLAUDE.md 里加几条硬规则：

- 🚫 **禁止修改或删除已有测试来"修复"失败**
- 🚫 **禁止纯 `assertNotNull` 式浅层断言**，每个断言必须验证具体值或状态变化
- 📊 **变异测试门禁 ≥ 60%**，覆盖率高但变异分数低就是不及格

## 写在最后

Kent Beck 发明 TDD 的时候，假设写代码的是人。人会分心、会偷懒、会过度工程化，所以需要红绿灯这套仪式来约束自己。

现在写代码的换了。AI 不会分心也不会偷懒，但它会浅层断言、会过度 mock、会偷偷删测试、会在上下文不够时犯低级错误。**病不一样，药方也得换。**

TDD 的灵魂——测试先行、测试即文档、测试驱动接口设计——比以往更关键。但执行方式得从"小步红绿灯"变成"一次交付、精确验证"。

好在 TDD 自己就教我们：**面对变化，先写测试。**
